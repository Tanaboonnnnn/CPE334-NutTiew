## 1. Decision and boundaries

| | Accepted Sprint 1 behavior | Revised contract |
|---|---|---|
| Q05: new Customer Booking | Start minus post-lock DB time is at least 60 minutes; 60:00 passes, 59:59 fails | Start minus post-lock DB time is at least 90 minutes (5,400 seconds); 90:00 passes, 89:59 fails |
| Customer availability | A single DB read timestamp projects eligible offers at the 60-minute cutoff | Same projection and clock at the 90-minute cutoff; display is indicative, never a reservation |
| Example: 15:00 Bangkok Slot | 14:00:00 is the last eligible instant | 13:30:00 is eligible; 13:30:01 is not. A request received at 13:29:59 but still waiting until 13:30:01 is too late. |

The team chose a longer preparation window for Tutors and Customers. #122 records the team's report of the 25 Nov class instruction: no separate instructor/TA approval is required. This is not a claim that anyone outside the team individually signed off. The revised contract and STS still require independent teammate review before the first implementation commit.

Only an authenticated Customer may create a Booking. Keep the current owner/session/CSRF checks, Slot validity/occupancy, Customer overlap, half-open adjacency, natural-key replay, private DTO and atomic transactions. A committed same-pair replay returns the existing Booking without applying a new cutoff. Do not repurpose the 90-minute threshold for Tutor Slot creation, 60-minute Slot duration (Q03), 60-day browse horizon, Customer cancellation (Q07: 30 minutes), either reschedule check (Q10/Q11: 60 minutes), or Tutor cancellation (Q18: 60 minutes). No retroactive change to existing Bookings or their timestamps.

Projection and write agreement is **at their respective server clocks**: one PostgreSQL `T_view` per read; PostgreSQL `T_elig` after required locks for new writes. Preserve precision: just below 90:00 (including a one-microsecond shortfall at the DB comparison) is ineligible; no integer-minute rounding or client-clock filtering. A valid guarded write can commit after the cutoff. Keep generic safe error mapping: cutoff → HTTP 422 `BOOKING_NOT_ELIGIBLE`; conflicting offers/Bookings retain their existing statuses. No new API fields, route, configuration, UI affordance or schema field.
